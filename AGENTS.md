## ⚠️ SECRETS — hard rule (identical in spirit to Home-ai)

This repo's remote is public-ish (`github.com/ninjass10101010-alt/Home-native`). **NEVER commit or echo a secret:** no `.env*` values (only `.env.example` placeholders ever), no NAS SSH creds, no PocketBase admin creds, no `SESSION_SECRET`/`ADMIN_SECRET`/`CRON_SECRET`, no `*_API_KEY`/`*_TOKEN`/`*_SECRET`. The session cookie is referenced by NAME only (`consuela_session`). PINs are memory-only in the app and are never written to any store, log, test, or file.

**Family privacy:** `reference/` and `screenshots/` contain real family names/photos and are **gitignored — local-only**. Family imagery never reaches the remote. Verify with `git check-ignore` if unsure.

**Before any push:** `bash scripts/security/push-safe.sh` — a hit means redact + commit + re-run.

## Toolchain (Expo SDK 57 — do not trust training data)

Expo ships breaking changes per SDK. Before writing code touching Expo/RN APIs: read the `expo` major version in `package.json`, consult versioned docs (`https://docs.expo.dev/versions/v<major>.0.0/` or `docs.expo.dev/llms.txt`). Recorded baseline: Expo SDK ~57, RN 0.86.3, React 19.2.3, Node 24. Dev deps were installed with `--legacy-peer-deps`; pins that MUST hold: `react-test-renderer@19.2.3` (matches React), `@react-native/jest-preset@0.86.3` (matches RN), `@testing-library/react-native@12.9.x` (v14 requires the `test-renderer` package and silently never-renders under our jest-expo wiring — do NOT upgrade past 12.x without proving `renderHook` works).

Routes live in `app/` (repo-root, expo-router). Non-route code lives in `src/`. Never create `src/app/`. ios/ and android/ are generated (CNG) — never hand-edit; configure via `app.json` + plugins. Local APK builds only (`expo prebuild` + Gradle); no EAS account, no Play Store.

**Updating the panel itself:** the tablet is updated over **adb/wifi** (`adb install -r` of the release APK, then `am force-stop` + `am start`) — **nothing else has to be rebuilt or redeployed**: the NAS stack, the web app and the API are untouched by that loop. The runbook is **`DEPLOY_TABLET_LOCAL.md` — LOCAL-ONLY** (gitignored, like the NAS one): it holds the household's addresses, the pairing steps and the debugging helpers, and it must never reach GitHub.

## Design contracts (summary — spec is authoritative)

- Single device: ApoloSign 1080×1920 portrait, Android 15. No phone/landscape/responsive modes.
- Type floor 14sp; tap targets ≥64dp; AA contrast light+dark+boost; token-only colors (`npm run tokens:check`).
- One nav surface: manifest-driven capsule dock (7 caps/role, kid swaps House→Rewards; More… 8/7/4); caps paint after auth hydration.
- Materials thin/regular/thick via one `Material` component; perf tiers via `perf.ts`; reduced-motion + boost honored.
- Backend: LAN HTTP to the Home-ai Next.js API layer (`http://nas.local:3000` default) — never direct to PocketBase or providers. Body fields win over HTTP status. Stale data is badged or hidden, never faked.
- A role is a CAPABILITY, not a label: `useAuth()` exposes `role` (`"parent" | "child" | "pet" | null`), which is non-null ONLY when a live whoami/sign-in confirmed the session (`null` = no live session = no capability; an unknown server role fails closed to `null`). EVERY gate that decides a CAPABILITY — a parent-only surface or action, a content rule, the wall's layout, the nav's role — reads `role` (`role === "parent"`, or `role !== null` for "is signed in"). The cached profile (`member`) is a DISPLAY fallback and grants NOTHING; only a DISPLAY read (a fallback name in a sentence) still reads `member`.
- Member avatars are ROSTER-FIRST and photo-aware. Resolve a member's identity through the live roster (`rosterMemberFor` in `src/tasks/board.ts`), never by trusting a stored `assigneeEmoji`/ledger glyph: a task row or ledger entry may carry a legacy full name ("Aurora Garcia") while the roster holds the current one, and the PB boundary collapses a photo member's glyph to `👤`. A photo avatar is a `data:image/...` URI and MUST render through `<Image>` (`isPhotoUri`); rendered as raw `<Text>` it stalls Android text layout (this froze the Tasks leaderboard). The ledger/task glyph is only the fallback for a non-member assignee ("Open", "Crew", "Grandma"). See `tests/tasks-page.test.tsx` § "roster-first avatars" and `tests/tasks-board.test.ts` § "filter options".
- Music is fully on-device: playback, search, and lyrics resolve through the NewPipe Extractor engine module `modules/youtube-engine/` (GPL-3.0) — no NAS proxy in the music path. The app is licensed GPL-3.0 (`LICENSE` + `NOTICE` at repo root); keep third-party attribution in `NOTICE` intact when adding bundled components. The `explicit` flag is TRI-STATE (`true` = badged explicit, `false` = NOT MARKED EXPLICIT — YouTube's search response carried no `MUSIC_EXPLICIT_BADGE` on that row, `null` = unknown/unrated): the rating is read from YouTube Music's own `MUSIC_EXPLICIT_BADGE` marker in the innertube search response, and the engine ships `explicitKnown` so the app always knows whether the ratings it holds are authoritative. The badge MARKS the explicit tracks; it does not certify the rest — so `false` is "not marked explicit", NEVER "rated clean". The kid policy lives in `src/music/explicit.ts` and FAILS CLOSED — while the filter is on, a kid role (child/pet/guest) sees a track only when its rating says it is not marked explicit; a parent sees everything and unrated rows are marked "Unrated" for them. The policy covers EVERY track surface, not just the search results: the `PlaybackProvider` computes it once from the viewer (`useAuth()` → the CAPABILITY `role === "parent"`, never the cached display profile) and the family setting (`settings.explicitFilter !== false`) and exposes it on its value, so the queue, the history, the downloads tray, the Now Playing panel, the MiniPlayer, the wall Music card and the auto-advance all read the SAME rule. A surface that shows or plays a track MUST filter through it (`visibleTracks`), and a track the viewer may not see must never be painted, queued, downloaded-shown or auto-advanced into — a parent → kid switch drops the hidden tracks from the queue and stops a hidden current track. That drop is DESTRUCTIVE: the hidden tracks are not restored when a parent signs back in (the device history still lists what was played). The NewPipe fallback yields `null` = unknown, so a kid sees nothing and the UI says why (a kid whose search ran on the fallback path is NEVER told "no songs matched" — an empty list must not read as "nothing found"). Read that policy before building UX on `explicit`: the field is tri-state, not a boolean. That policy now carries TWO rules (`isContentHidden`): the RATED-EXPLICIT rule, and the FAMILY'S OWN deny-list. The deny-list is NOT a content rating — it is a list the family NAMES themselves (no content analysis, no third-party rating, no per-kid profile) — and it is DEVICE-LOCAL (AsyncStorage, key `music.denylist`), edited by a PARENT in the MUSIC SCREEN behind a parent-only "Blocked" button (a kid role never sees the control, the modal or the list). ONE list, matched CASE-INSENSITIVELY AS A SUBSTRING against BOTH the artist and the track title, and the deny rule holds INDEPENDENTLY of the explicit filter setting (turning the filter off governs the badge, never the family's own list). A denied track is hidden from kid roles on EVERY surface, exactly like a badged one: the `PlaybackProvider` carries the normalized terms in the SAME role-aware policy, so the search results, the queue, the history shelf, the downloads tray, the Now Playing panel, the MiniPlayer, the wall music card and the auto-advance all inherit it — a denied track is never painted, queued or auto-advanced into — while a parent still sees it, marked "Blocked for kids". Read the deny-list SPEC (`../docs/superpowers/specs/2026-10-21-home-native-music-deny-list-design.md`) BEFORE building any UX on the deny-list: it is the family's own decision, and the UI must never present it as a rating. RESOLVED (the policy's ENTRY POINT, SP1.7): the policy's parent flag now comes from the CAPABILITY role (`useAuth()` → `role`), which is non-null ONLY when a live whoami/sign-in confirmed the session — so a cached parent profile can no longer unlock explicit content or the family's blocked artists, and the filter is exactly as strong as the live session behind it. A gate that decides a CAPABILITY reads `role`; only a DISPLAY read still reads the cached `member`. KNOWN LIMIT (a SOURCE gap, accepted risk): the badge is ONE-SIDED — YouTube does not badge EVERY song row (e.g. Eminem's "Till I Collapse" comes back with `badges: null`), so a song YouTube does not badge can reach a kid. The badge alone cannot be the only signal, but an unbadged row must NOT be treated as unrated in a follow-up: Adele's "Hello" (id `yjo_aXygRDI`) arrives with NO `badges` key at all (captured fixture), so "unbadged ⇒ unrated" would hide every clean song and empty the kids' music surface. The SECOND signal is now SHIPPED — the family's own deny-list (above) — but it is a signal only for what the family NAMED: an unbadged explicit song the family has not named is STILL reachable. The deny-list is a second signal the family controls, not a rating.
